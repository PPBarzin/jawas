# Diagnostic production des 6 et 7 mai 2026

## Objet

Cette note reconstruit ce qui s'est passe les `6 mai 2026` et `7 mai 2026` a partir des vrais fichiers de production copies depuis le container:

- `hunter_trace.jsonl`
- `hunter_signal_metrics.jsonl`

L'objectif est de distinguer:

- les signaux recus trop tard
- les signaux non resolus
- les cas ou le hunter tire effectivement

## Source de verite

Le point important est que les fichiers actifs etaient dans le container Docker, pas dans la racine du host. Les analyses precedentes faites sur les fichiers host etaient donc biaisees.

Le code confirme aussi la semantique des traces:

- `elapsed_ms` est mesure depuis `ws_received_at_ms`
- les etapes `firing` et `bundle_sent` sont journalisees dans le hunter

## Resume executif

La lecture dominante est la suivante:

1. Le bot n'est pas principalement en train de perdre a l'execution.
2. Le probleme principal des `6` et `7 mai 2026` est un probleme de temporalite du signal.
3. Quand le bot recoit un signal exploitable, il sait encore tirer et envoyer un bundle.
4. Une partie non negligeable du flux est aussi perdue avant tir sur `signal_resolution_failed`.

Formulation courte:

> Jawas perd d'abord a la detection temporelle, pas d'abord au bundle path.

## Volumes observes dans `hunter_trace.jsonl`

### 6 mai 2026

- `246` evenements `skip` avec raison `source_obligation_healthy`
- `28` evenements `error` avec raison `signal_resolution_failed`
- `3` evenements `firing`
- `3` evenements `bundle_sent`

### 7 mai 2026

- `148` evenements `skip` avec raison `source_obligation_healthy`
- `8` evenements `error` avec raison `signal_resolution_failed`
- `1` evenement `firing`
- `1` evenement `bundle_sent`

### Lecture

Le ratio est tres desequilibre:

- `394` cas "signal vu, mais obligation deja saine"
- `36` cas "signal vu, mais non resolu"
- `4` cas "signal vu, resolution OK, tir effectif, bundle envoye"

Autrement dit, sur cette fenetre, le funnel est massivement casse avant le tir.

## Ce que disent les traces

### 1. Le cas dominant est `source_obligation_healthy`

Le hunter recoit un signal, inspecte l'opportunite, et constate deja:

- `Obligation is healthy`
- ou `Cannot liquidate healthy obligations`

Ce pattern signifie que le signal de liquidation est majoritairement recu apres la fenetre utile.

### 2. Le second probleme est `signal_resolution_failed`

Le cluster le plus net apparait le `6 mai 2026` autour de `06:09Z` a `06:36Z`, avec une serie de:

- `ws_received`
- puis `signal_resolution_failed`
- detail: `source=primary_rpc no KLEND liquidate instruction found`

Ce n'est pas une latence de bundle. C'est un echec de resolution du signal entrant.

### 3. Le path d'execution n'est pas mort

Les succes observes sur cette fenetre:

- `2026-05-06T10:40:52Z` `bundle_sent`
- `2026-05-06T16:06:58Z` `bundle_sent`
- `2026-05-06T21:07:01Z` `bundle_sent`
- `2026-05-07T06:53:01Z` `bundle_sent`

Donc:

- la machine tourne
- le hunter peut encore construire et envoyer
- Jito n'est pas le facteur explicatif principal de la sous-performance visible ici

## Ce que dit `hunter_signal_metrics.jsonl`

`hunter_signal_metrics.jsonl` ne decrit pas tous les evenements bruts. Il synthestise surtout les opportunites qui entrent dans le systeme de lock et leur issue finale.

Sur la fenetre `6-7 mai 2026`, on y voit:

- `2026-05-06`: `3` `bundle_sent`, `4` `skipped`
- `2026-05-07`: `1` `bundle_sent`

Cette vue est utile pour les opportunites "retenues", mais elle ne remplace pas `hunter_trace.jsonl` pour mesurer le bruit amont. C'est la raison pour laquelle les comptes sont plus faibles que dans la trace brute.

## Conclusion

Le diagnostic le plus solide pour les `6` et `7 mai 2026` est:

- le bot recoit beaucoup de signaux trop tardifs
- une partie du reste echoue encore a la resolution
- quand un signal exploitable arrive vraiment, le script reagit assez vite et peut envoyer

La conclusion de recherche qui en sort est coherente avec l'intuition du projet:

> un bot reactif sur Solana peut etre structurellement en retard avant meme d'entrer dans sa propre phase d'execution.

## Limites

- Les donnees de cette note proviennent des JSONL de production copies localement, pas d'une capture live.
- La source de signal est marquee `primary_rpc` dans ces logs, donc cette note ne permet pas d'isoler specifiquement `Helius` sur cette fenetre.
- `hunter_trace.jsonl` contient aussi du bruit de format hors du sous-ensemble exploite ici. Il reste utilisable, mais l'observabilite n'est pas encore totalement propre.
